## Review: byte-prefix output path (stock-output-prefix-20261019)

**Scope reviewed:** `src/jdbc/chdb/byte_output.cljc`, `resources/jdbc/chdb/output_prefix_write.ss`, `test/jdbc/chdb_byte_output_test.cljc`, `src/jdbc/chdb/durable/wal.cljc`.

### No defects found. Design holds up under the targeted checks below; a couple of non-bug observations are noted.

**File-only stream admission** — `output_prefix_write.ss` gates admission in two layers: (1) a capability probe over `out-stream-live-port`/`jnum->exact` (bound, procedure, correct arity) plus record-type-uid/field-name checks on the `jhost`/`jolt-array` record shapes, guarding against a stale or incompatible runtime; (2) the per-call predicate requires `jhost?`, tag `"out-stream"`, a 3-slot state vector with slots 1 and 2 both false, and the wrapped port satisfying `port?`, `file-port?`, `binary-port?`, `output-port?`. Any wrapper around a custom/pipe/non-file port, or a raw (non-jhost) Java stream, correctly fails admission and falls through to ordinary dispatch. This matches the custom-native-port and pipe tests, both of which assert zero native writes and correct fallback behavior.

**Byte-prefix bounds** — bounds are checked twice, consistently: in Clojure, `try-write!` requires `bytes?`, `integer? length`, and `(<= 0 length (alength bytes))` before ever calling into the kernel; in Scheme, the predicate independently requires `(fixnum? n)`, `(fx>=? n 0)`, `(fx<=? n (bytevector-length backing))`. Both reject out-of-range or non-fixnum counts (e.g. the test's `3N` bignum case still works via `jnum->exact`/`fixnum?`), and both decline (rather than throw) on violation, which correctly routes back to ordinary `.write` semantics including its own argument-validation errors. No gap between the two layers' length sources (Java array length vs. backing bytevector length) was found — they describe the same buffer.

**Fallback / closed / custom / pipe effects** — Declined admission in `write-prefix!` falls straight to `(.write ^OutputStream output bytes 0 length)`, preserving the exact exception class/message for a closed stream (verified against the non-helper call in the test), the custom `OutputStream` proxy's 3-arg dispatch (including for `n = -1`, which is passed through unmodified rather than being special-cased), and a piped stream's implicit-flush/read-visibility behavior. No flush/close is ever invoked by the helper itself in any of these paths, matching the stated "borrow only" contract in the docstring.

**No retry after partial write** — `try-write!`'s `and` chain does not wrap the native call in `try`/`catch`; an exception thrown mid-write by the native closure propagates directly out of `write-prefix!` with no fallback attempt. The redef-based test confirms this: the stand-in kernel writes one byte, then throws, and the assertions show the output stream retains exactly that one byte and the kernel was invoked exactly once — i.e., `write-prefix!` never re-issues the write through the ordinary path after a native attempt has started. This matches the explicit comment "Never retry an attempted/partial write" and is a correctness-critical property given the byte stream can't be un-written.

**WAL ownership/error propagation** — `wal.cljc`'s `write-prepared!` iterates `:chunks` and calls `byte-output/write-prefix!` once per chunk with no surrounding `try`/`catch`; if any chunk throws (including a native partial-write), the `doseq` stops and the exception propagates unmodified to the caller, with any already-written earlier chunks left durably on the stream. This is consistent with the documented contract ("Counters advance only after this entire call succeeds") — the byte-accounting/replay counters live outside this function and are expected to not advance on exception, leaving recovery of a partially-flushed tail record to the caller/replay logic (not in scope of the reviewed files). `native-prepared-line`'s `valid?` check (bounds 1 ≤ used ≤ alength ≤ 65536, total matches sum) runs at *prepare* time, before any bytes are written, so an invalid descriptor is rejected pre-write and can't cause a partial WAL write by itself.

**Observations (not defects):**
- `native-prepared-line`'s per-chunk bound requires `used ≥ 1`, i.e. it rejects zero-length chunks; this appears to be an intentional invariant of the chunk encoder rather than a gap, since `write-prefix!` itself still supports zero-length writes fine on the plain path.
- The `output-prefix` delay only catches `Throwable` around `scheme/eval-string` (load-time), not around later invocations — intentional, since catching call-time errors there would reintroduce the "retry after partial write" risk the design explicitly avoids.
