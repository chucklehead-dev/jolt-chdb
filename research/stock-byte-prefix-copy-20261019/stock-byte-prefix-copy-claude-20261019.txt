## Review: byte-prefix copy change

**Core architectural tradeoff (flag for author confirmation, not a bug):** `byte_prefix_copy.ss` intentionally skips the temporary-bytevector copy that stock `ffi/write-array` performs before invoking `sa-foreign-bytes-set!`, passing the caller's own backing bytevector directly (comment, lines 1–3). The docstring in `byte_copy.clj:18` compensates by pushing a new contract onto callers: "Source must not race with this call." This is a real narrowing of the safety envelope versus before — if the temp-copy in stock `ffi/write-array` existed for any reason beyond "same primitive, different buffer" (e.g., isolating the native call from concurrent mutation of caller-visible memory), this path no longer provides that isolation. All three current call sites look race-free: `owned_statement.clj`'s `with-query-buffer` copies a private immutable per-statement snapshot (never touched elsewhere after `try-snapshot`), and `digest.cljc`'s two callers use a loop-local `managed-buffer` or caller bytes assumed static for the call's duration. But `digest/sha256-bytes` is public, and nothing in this diff enforces the no-race contract on external callers — it's advisory only.

**Unverifiable trust boundary:** The whole safety argument rests on `jolt.ffi`, `jolt.scheme`, and the native `sa-foreign-bytes-set!`/`ffi/write-array` implementations, none of which are in the reviewed file set. I can't independently confirm that `sa-foreign-bytes-set!` never writes past `n` bytes, that `jnum->exact` on `pointer` can't silently truncate/misinterpret an address, or that the Chez `procedure-arity-mask` bit convention (`bitwise-bit-set? mask 3` at `byte_prefix_copy.ss:6`) reliably means "accepts exactly 3 args" rather than something else (e.g., variadic encoding). This is an assumption inherited from the existing runtime, not something newly introduced, but it's the single point every other guard depends on.

**GC-during-copy is untested, GC-after-copy is:** `prefix-copy-retains-guards-and-source-through-gc` (chdb_byte_copy_test.clj:32) calls `System/gc` *after* `write-prefix!` returns, which validates no stale-reference corruption post-call but does not inject a collection *during* the native primitive invocation. This is almost certainly fine under Chez's non-preemptive, allocation-triggered GC model (no Scheme allocation happens between entering and returning from the FFI call), but the test doesn't prove that assumption — it's inherited from however stock `ffi/write-array` already relies on the same non-collect-safe primitive.

**Things that check out:**
- Bounds are enforced twice independently — Clojure-side (`<= 0 length (alength bytes)`) and inside the `.ss` kernel against the actual `bytevector-length` of the backing store — so even if the two length sources ever diverged, the inner check is the final authoritative gate before the native call.
- Zero-length short-circuits to `0` in `byte_copy.clj:23` before touching `@prefix-copy` or `ffi/write-array` at all, so `ffi/null` + length `0` is safe by construction (verified by test).
- Failure semantics match the docstring exactly: no try/catch wraps the `@prefix-copy` call in `write-prefix!`, so a post-effect copy failure propagates without a retried fallback (structurally confirmed, and exercised by `copy-failure-is-not-retried-through-fallback`).
- Kind/UID/backing/arity are all fenced before the primitive is ever called, and both "no adapter bound" and "non-bytevector-backed jolt-array" cases correctly fall through to ordinary `ffi/write-array` (exercised by `fallback-and-boxed-byte-backing-are-correct`).
- `digest.cljc`'s per-iteration `write-prefix!` call only copies the `n` bytes actually read into a reused 65536-byte buffer, correctly avoiding hashing stale tail bytes from a prior iteration — no behavior change versus a full-buffer copy for this case since only `n` bytes are ever digested.
- SHA-256 known-answer values for `"abc"` and the empty string in `chdb_durable_digest_test.cljc` are both correct against the standard test vectors.

**Limitation:** I did not run anything; this is read-only inspection of the seven listed files only.
