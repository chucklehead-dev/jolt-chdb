**Does it remove writer-side rescanning without exposing cached arrays?** Yes, with the mechanism verified consistent.

**Rescanning removed, correctly:** `owned-statement/precompute-wal` eagerly runs `encode-wal` once (idempotent — `(.-prepared statement)` short-circuits a second call) and stores the result as a `PreparedWalRecord` (`byte_record.cljc`/`owned_statement.clj:24-32`). `writer.clj:293-312`'s `prepare-wal-line!` calls `owned-statement/prepared-wal-for-write`, which returns that cached opaque record directly instead of re-running `encode-wal` (the JSON/WAL scan) per execute. `durable/wal.cljc:104-116`'s `prepared-size`/`write-prepared!` dispatch on `satisfies? byte-record/ByteRecord` and delegate to `write-to!`, so the writer never touches raw chunk arrays itself.

**No cached-array exposure:** Two separate guards enforce this. (1) The *public* API `owned-statement/prepared-wal` always `aclone`s each chunk before returning (`owned_statement.clj:89-92`) — public callers only ever see copies, confirmed by the test mutating `(first (first (:chunks public)))` and then re-verifying unaffected re-encode bytes. (2) The *writer-only* `prepared-wal-for-write` returns the raw cached record, but its `write-to!` routes every byte through `byte-output/write-private-prefix!` (`byte_output.cljc:32-42`), which `aclone`s before handing bytes to any ordinary `OutputStream.write`, and only skips the clone for a behaviorally-probed qualified native file port that borrows bytes synchronously without retaining them. The `custom-stream-mutation-and-retention-cannot-poison-private-record` test proves this: a proxy stream that retains and later mutates the array it was given does not affect subsequent re-encodes of the same cached record, because it received a clone, not the private backing array.

**Snapshot/WAL bytes unchanged:** `precomputed-record-is-opaque-and-public-chunks-stay-independent` byte-compares the cached record's output against `wal/portable-line-bytes` (the compatibility oracle) for empty, ASCII-boundary, and ~128KiB inputs, including a real `FileOutputStream` round-trip. Bytes are identical; caching only changes *when* encoding happens, not what it produces.

**128 MiB cap (6N+11) correctness:** `max-precomputed-input-bytes` = `(128 MiB − 11) / 6` (`owned_statement.clj:11`) bounds the input size for which *caching* is attempted, matching the worst-case JSON-escaping expansion (6 bytes per input byte, 11 bytes of `{"sql":"..."}\n` framing overhead). This is a conservative *precompute-eligibility* guard, not a replacement for the authoritative segment-size check. The real 128 MiB WAL-segment limit is still enforced exactly, post-encode, on actual (not worst-case) bytes inside `prepare-wal-line!` (`writer.clj:308-311`, `next-segment-bytes > max-wal-segment-bytes`) — this check runs identically whether the line came from the cache or from a fresh `encode-wal`. Statements whose raw size exceeds the precompute cap simply decline caching and fall back to the pre-existing on-demand `encode-wal` path (verified by `prepare-once-before-worker-and-decline-oversized-cache`, which also confirms the 64 MiB `max-statement-bytes` statement-size check in `validate-statement-size!` is untouched and independent).

**Admission order / sealed-spool / partial-failure / acknowledgement unchanged:** In `do-execute-owned-and-flush!` (`writer.clj:406-420`) the order remains: `assert-writable!` → statement-type check → `reject-sealed-wal!` → `prepare-wal-line!` (size validation, sealed re-check, encode-or-reuse, segment-limit check) → native admitted-buffer policy authorization → `execute-admitted!`. Nothing in the precompute change reorders these. `cached-record-keeps-writer-policy-and-partial-append-boundaries` exercises all three outcomes against a *cached* record — success, policy rejection (zero native calls, nothing published), and injected partial-append failure (`write-private-prefix!` writes 1 byte then throws) — and confirms `require-checkpoint!` fires, `pending-statements` is zero, and nothing is published, identical to the pre-existing non-cached partial-failure contract. The `otel/exporter/chdb.clj:1294-1307` integration point only adds a `try-snapshot`/`precompute-wal` call on an already-produced byte buffer before falling into the pre-existing `execute-durable-sql!` dispatch (`chdb.clj:1509-1514`, which already branched on `string?` vs owned-statement); it does not alter that dispatch or bypass `require-order!`/snapshot-consistency checks surrounding it.

**Ordinary (non-owned, non-precomputed) paths:** `wal/write-prepared!`'s map-chunk branch still uses the non-private `byte-output/write-prefix!` (no forced clone) since those chunks are freshly generated, not shared cached state — this path is untouched by the change.

No findings of leaked mutable aliasing, snapshot/WAL byte divergence, cap miscalculation, or admission/sealed-spool/partial-failure/acknowledgement regression.
